• Schemas: each tool has a name, a description written for the model (what it does, when to use it, what it returns), and a strict JSON Schema for arguments (types, enums, formats, required fields, additionalProperties: false).
  • Validation: validate arguments in code before execution; return clear, structured errors the model can act on ("order_id must match A-\d{4}").
  • Scoped permissions: the agent acts on behalf of a user with that user's permissions, or with a narrowly scoped service identity. Prefer read-only tools; separate "propose" from "commit"; scope tokens to the tenant and the task; never give an agent a generic admin credential.
  • Safe execution: timeouts, rate limits, result-size limits, sandboxes for code execution (containers, gVisor/Firecracker microVMs, no network or an allowlist), dry-run modes, and allowlists of hosts/commands.
  • Tool results are untrusted input: a web page or email returned by a tool may contain instructions. Label them as data and keep high-impact actions behind approval (16.2).
Example: a tight schema
{"name": "issue_credit",
 "description": "Propose a goodwill credit on an order. Use only after get_order confirms a qualifying issue. Returns a proposal ID; credits over 50 USD wait for human approval.",
 "parameters": {"type": "object", "additionalProperties": false,
   "required": ["order_id", "reason_code"],
   "properties": {
     "order_id":    {"type": "string", "pattern": "^A-[0-9]{4}$"},
     "reason_code": {"type": "string", "enum": ["late_delivery", "damaged", "missing_item"]}}}}

Note that the amount is not a parameter: code computes it from the reason code and order total, removing a whole class of model errors.
