Intuition

You press "Pay" and the page freezes. Did it work? If you press again and it pays twice, the system was not safe to retry. An idempotency key is a receipt number sent with the request: if the same number arrives again, the shop shows the first receipt instead of charging again.

Some steps cannot be retried away. When a trip has a flight, a hotel and a payment and the payment fails, the flight and hotel must be cancelled. That chain of steps, each with its undo, is a saga.

Mechanism

Idempotent operation: doing it twice has the same effect as once ("set status = shipped" is idempotent; "add $10 credit" is not, unless keyed).
Idempotency key: a unique key sent with a non-idempotent request; the server stores the result under the key and returns it for duplicates. Derive it deterministically from (task, step, arguments), not randomly per attempt.
Compensating action: an action that semantically undoes an earlier one when a later step fails (cancel the booking, reverse the charge). A multi-step process with compensations is a saga.

Duplicate actions in agents come from network retries, crash-resume, and the model itself deciding to call the same tool again ("let me try that again"). Defences: idempotency keys at the tool layer, deduplication of identical calls within a task, and checking current state before acting ("does a credit for this order already exist?").

The crash window. A crash between a tool call and the next checkpoint is the classic duplicate: the action happened, but the saved state says it did not, so the resumed run repeats it. Idempotency keys make that retry safe. When a business change must also publish an event or notify another system, use a transactional outbox: write the change and an "outbox" row in one database transaction, and let a separate relay deliver the event, so the two can never disagree.

Example: idempotency at the tool layer
def create_credit(task_id: str, order_id: str, reason: str, db) -> dict:
    key = f"{task_id}:create_credit:{order_id}:{reason}"            # deterministic
    if (existing := db.get_by_idempotency_key(key)): return existing   # duplicate → same result
    amount = policy.credit_amount(order_id, reason)                    # computed in code
    return db.insert_credit(order_id, amount, idempotency_key=key)     # unique constraint on key

The numbers

Duplicates from retries (illustrative). Suppose 1 call in 100 times out after the write succeeded, and the client retries.

  • At 20,000 refunds a day, 20,000 × 0.01 = 200 refunds are paid twice without a key.
  • At an average of 1,500 rupees each, that is 200 × 1,500 = 300,000 rupees a day paid out by mistake.
  • With a key built from the task, the action and the arguments, the retry returns the stored result: 0 duplicates.

A random key per attempt does not help: each retry looks like a new request.

Code

The program sends 100 of your project’s money movements through a server that loses 30% of its replies after writing. Retrying with a new key each time pays some twice; a key derived from the record and action does not. Set LOST_REPLY to 0.05 and run it again.
