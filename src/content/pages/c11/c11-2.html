Intuition

An agent works like someone solving a problem at a help desk: decide what to check, check it, look at what came back, and decide again. This loop is simple. The hard part is knowing when to stop.

A person stops when the job is done, when they notice they are going round in circles, or when it is taking far too long. An agent only stops for those reasons if code makes it: a step limit, a budget, a deadline and a check for repeated calls.

Mechanism

The basic agent loop (often called ReAct: reason + act): the model receives the goal, the tool list and the history; it either calls a tool or gives a final answer; the tool result (observation) is appended; repeat. Tool selection depends on clear tool names and descriptions, few overlapping tools, and examples. Planning can be implicit (decide one step at a time) or explicit (write a plan first, then execute and revise it), which helps on long tasks and makes traces readable.

Termination must be engineered, not hoped for: final-answer detection, a maximum number of steps, a token/cost budget, a wall-clock deadline, loop detection (same tool with same arguments twice), and a "give up and escalate" path.

The numbers

Steps add up (illustrative). If one step, a model call plus a tool call, costs 0.012 dollars:

  • A normal run of 3 steps costs 3 × 0.012 = 0.036 dollars.
  • A run that wanders until a 6-step limit costs 6 × 0.012 = 0.072 dollars, twice as much, and produces nothing.
  • With a budget of 0.05 dollars, it stops after 4 steps, since 5 × 0.012 = 0.06 would go over.

Loops at scale. If 2% of 10,000 daily tasks loop until a limit of 20 steps, that is 200 × 20 = 4,000 wasted steps a day, more than the 3,000 steps that 1,000 normal tasks need.

Code

The program runs a scripted agent loop on a case from your project: a normal run, one that repeats a call and one that never decides. The tool choices are scripted, so the termination rules are what you see. Change MAX_STEPS or BUDGET and run it again.

Laptop lab: a minimal agent loop with real termination rules Laptop · CPU
import json, ollama
ORDERS = {"A-1043": {"status": "delivered_late", "paid": 120.0}}
def get_order(order_id: str) -> str:
    """Return order status and amount paid as JSON."""
    return json.dumps(ORDERS.get(order_id, {"error": "not found"}))
def propose_credit(order_id: str, amount: float) -> str:
    """Propose a credit for an order. Requires human approval before it is applied."""
    return json.dumps({"proposal_id": "P-1", "order_id": order_id, "amount": amount, "status": "pending_approval"})
TOOLS = {"get_order": get_order, "propose_credit": propose_credit}

def run(task, max_steps=6):
    msgs = [{"role": "system", "content": "You resolve order issues. Late delivery earns a 10% credit. "
                                          "Use tools; never invent order data. Stop when done."},
            {"role": "user", "content": task}]
    seen = set()
    for step in range(max_steps):
        r = ollama.chat(model="qwen2.5:1.5b", messages=msgs, tools=list(TOOLS.values()))
        msgs.append(r.message)
        if not r.message.tool_calls: return r.message.content            # final answer
        for c in r.message.tool_calls:
            key = (c.function.name, json.dumps(c.function.arguments, sort_keys=True))
            if key in seen: return "ESCALATE: loop detected"                 # same call twice
            seen.add(key)
            fn = TOOLS.get(c.function.name)
            out = fn(**c.function.arguments) if fn else json.dumps({"error": "unknown tool"})
            print(f"step {step}: {c.function.name}{c.function.arguments} -> {out}")
            msgs.append({"role": "tool", "content": out, "tool_name": c.function.name})
    return "ESCALATE: step limit reached"
print(run("Order A-1043 arrived late. Sort it out."))

Run it several times: a small model will sometimes compute the credit wrongly or skip the lookup. That is exactly why the credit amount should be computed in code (7.7) and why agents need evaluation over repeated runs (8.8).
