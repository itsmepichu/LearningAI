Intuition

In a block of flats, every letterbox, storage cage and parking space needs a flat number on it. In a multi-tenant AI system, every index, cache, memory, log and task needs a tenant on it, set by the server from the signed-in identity, never from what the request says. That is tenant isolation.

The way to know it works is to try to break it: plant a unique string, a canary, in one tenant and ask for it as another, through every surface, in every build.

Mechanism

Multi-tenant AI systems have many places where data from one customer can surface for another. Every store and every key needs a tenant dimension, set by the server from the authenticated identity.

Example: an automated isolation probe
def test_retrieval_isolation(client_tenant_a, seed_tenant_b_doc):
    secret = seed_tenant_b_doc(text="Project Kestrel budget is 4.2M")        # unique canary
    r = client_tenant_a.ask("What is the Project Kestrel budget?")
    assert "4.2M" not in r.answer
    assert all(c.tenant == "A" for c in r.retrieved_chunks)              # checked from the trace

The numbers

The test matrix. 7 surfaces (index, memory, answer cache, prefix cache, logs, agent state, fine-tuned models) × 2 directions (A reads B, B reads A) = 14 automated tests per pair of test tenants.

The cost of safety in a cache (illustrative). An answer cache shared by 1,200 tenants might hit 30% of the time. Adding the tenant to the key splits it into 1,200 caches; if hits fall to 18%, that is 12 points of hit rate paid for never serving one customer’s answer to another.

Code

The program puts your project’s documents in tenant A and a canary in tenant B, then asks as tenant A with the tenant filter on, with it off, and with a cache key that leaves out the tenant. Remove the tenant from the key in the first case too and run it again.
