Intuition

Capacity planning turns "we have two million users" into "we need to answer 150 requests a second at the busiest minute". Each step multiplies: how many use the feature on a day, how often, how bunched up at the busy hour, and how bursty within it.

Little’s law then says how many requests are inside the system at once: arrivals per second times seconds each one stays. That number sizes connection pools, GPU slots and rate limits.

Mechanism

Work through a chain of assumptions, each of which you should measure from product analytics or a pilot:

  1. Registered users → daily active users of the AI feature (activation rate).
  2. × requests per active user per day → requests per day.
  3. Requests concentrate in busy hours: peak-hour share (e.g. 15% of the day's requests in the peak hour), and within the hour a further burst factor (peak minute vs hour average, often 1.5–3×).
  4. → peak requests per second (RPS).
  5. Little’s law: concurrency = arrival rate × time in system. 50 RPS × 8 s average = 400 requests in flight. This sizes connection pools, GPU batch slots and rate limits. Little's law gives the average in flight for a stable system (arrivals below capacity); it is not a p99 or burst figure, so plan headroom above it.
  6. × tokens per request → peak input and output tokens/second, which sizes model capacity or API rate limits.
  7. Add background workload: ingestion and re-embedding (chapter 10), evaluation runs, batch summarisation, agent jobs, which should be scheduled away from peaks.
Example: the default numbers

10M registered × 8% = 800k DAU × 6 = 4.8M requests/day. 12% in the peak hour = 576k/hour = 160 RPS average, × 2 burst = 320 RPS at the peak minute. × 6 s = ~1,900 requests in flight. Output: 320 × 350 = 112k output tokens/s; input 960k tokens/s (much of it cacheable system prompt). That is a large deployment, and every assumption deserves a measurement before buying capacity.

The numbers

The default chain (illustrative).

  • 10 million registered × 8% active = 800,000 users a day × 6 requests = 4.8 million requests a day.
  • 12% in the busiest hour: 576,000 ÷ 3,600 seconds = 160 a second on average in that hour.
  • The busiest minute is twice the hour’s average: 320 a second.
  • Each request takes 6 seconds, so 320 × 6 ≈ 1,900 requests are in flight at once.
  • Output: 320 × 350 tokens = 112,000 tokens a second.

Code

The program measures how much busier the busiest day is than an average day in your project’s dated records, then runs the chain from users to peak requests, requests in flight and output tokens for both. Change PEAK_HOUR or BURST and run it again.
