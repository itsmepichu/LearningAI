Tensor: an n-dimensional array (a scalar is 0-D, a vector 1-D, a matrix 2-D; a batch of token embeddings is 3-D: batch × sequence × dimension). Frameworks run tensor operations on CPU or GPU.
CPU: a few to a few dozen powerful cores, optimised for branching, sequential logic. GPU: thousands of simpler cores plus specialised matrix units (Tensor Cores), optimised for doing the same arithmetic on huge arrays.
FLOPs: floating-point operations; a measure of compute. Memory bandwidth: bytes per second that can be read from memory. Many AI workloads are limited by bandwidth, not FLOPs.
Precision: bits per number. FP32 (4 bytes), FP16/BF16 (2 bytes), FP8 and INT8 (1 byte), INT4 (0.5 byte). Fewer bits = less memory and faster, with some accuracy loss.

A rule of thumb you will use constantly: model memory ≈ parameters × bytes per parameter. An 8B model needs about 16 GB in BF16, 8 GB in INT8 and 4–5 GB in 4-bit. Your laptop's RAM bounds which models you can run; a GPU's VRAM bounds what it can serve, and inference needs extra memory for the KV cache (14.1).

Why GPUs are faster for AI: generating one token from an 8B model needs ~16 GB of weights read from memory. A laptop with ~60–100 GB/s memory bandwidth can do that at most ~4–6 times a second at BF16; a datacentre GPU with several TB/s of HBM bandwidth can do it hundreds of times a second. Quantising to 4-bit reads a quarter of the bytes, which is why quantised models run usefully on laptops.

FP16 vs BF16. Both use 2 bytes. FP16 has more precision (10-bit mantissa) but a small range (largest value ≈ 65,504), so large activations overflow and training needs loss scaling. BF16 keeps FP32's 8-bit exponent, so it has the same range as FP32 with less precision (7-bit mantissa). That is why most LLM training and serving use BF16. Units: this manual writes GB = 10⁹ bytes and GiB = 2³⁰ bytes (≈ 1.074 GB); per-token KV sizes are given in KiB (1,024 bytes). Mixing the two silently introduces a 7% error at GB scale.

Example: will it run on my laptop?

A 16 GB laptop. Operating system and apps use ~5 GB, leaving ~11 GB. A 3B model at 4-bit ≈ 2 GB: comfortable. An 8B model at 4-bit ≈ 5 GB: works, a few tokens per second. A 70B model at 4-bit ≈ 40 GB: does not fit. Use a hosted API or rented GPU for that.

Laptop lab: measure your bandwidth ceiling Laptop · CPU
import numpy as np, time
a = np.ones(500_000_000 // 8)        # ~500 MB of float64
t = time.perf_counter(); s = a.sum(); dt = time.perf_counter() - t
print(f"~{a.nbytes/dt/1e9:.1f} GB/s effective read bandwidth")
# tokens/sec upper bound for a model of size M GB ≈ bandwidth / M
for m in (0.8, 2.0, 4.5): print(f"{m} GB model → ≤ {a.nbytes/dt/1e9/m:.0f} tok/s")

This single-threaded NumPy read underestimates true bandwidth, but it shows why model size in bytes, not parameter count alone, sets your CPU generation speed.
