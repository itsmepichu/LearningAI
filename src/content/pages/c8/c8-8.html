Intuition

Grading an agent by its final message is like grading a plumber by what they say at the door. You need to check the pipes: did they use the right tools, did they do it in a sensible order, is the leak actually fixed, and did they tell you the truth about what they did?

Agents also do not behave the same way every time. One success in five tries is not good enough for a job that runs every day, so test each case several times and count how often all of the runs succeed.

Mechanism

An agent (chapter 11) takes many steps, so a correct final message can hide unsafe or wasteful behaviour, and an awkward message can follow a perfectly executed task. Evaluate four levels:

  1. Tool use: right tool chosen, valid arguments, no forbidden calls, permission errors handled.
  2. Execution trace (trajectory): number of steps, loops, redundant calls, recovery from errors, time and tokens consumed.
  3. Resulting state: inspect the environment after the run. Was the ticket actually updated? Was exactly one refund created? Nothing else changed? This is usually the most important check and is fully deterministic.
  4. Final answer: correct, honest about what was done, appropriate tone.

Run agents in a sandboxed, resettable environment (test database, mocked APIs) seeded per case, run each case several times because agents are non-deterministic, and report pass@k (succeeded at least once in k runs) and pass^k (succeeded in all k runs; what reliability requires).

Check invariants, not one golden path. Requiring an exact tool sequence rejects valid, often cheaper, solutions. Assert properties instead: the end state is correct, no forbidden or unauthorised call happened, the step and cost limits held, and the final message matches what was actually done. Do not require the model's hidden chain-of-thought as evidence; the tool proposals, tool results and state changes are the observable, auditable record.

Example: pass@k vs pass^k

An agent succeeds 80% of the time per run, independently. pass@5 = 1 − 0.2⁵ ≈ 99.97%, which looks great. pass^5 = 0.8⁵ ≈ 33%, which shows that in a workflow run five times a day, a failure almost every day is likely. Production readiness depends on the second number.

Toolbox for evaluation

promptfoo
prompt/model evals · red teaming · CI

YAML test cases with assertions (contains, JSON schema, LLM rubric), side-by-side model comparison, CI integration. Works against Ollama locally.

Inspect
evals framework · agents · sandboxes

From the UK AI Security Institute. Datasets, solvers, scorers, tool use and Docker sandboxes for agent evals. Good for rigorous agent tasks.

Ragas
RAG metrics

Faithfulness, answer relevancy, context precision/recall and test-set generation. Uses an LLM judge; calibrate it (8.3).

DeepEval
pytest-style LLM tests

Unit-test style metrics (G-Eval, hallucination, tool correctness) that run in CI.

lm-evaluation-harness
model benchmarks

Standard academic benchmarks on any HF or API model. Use to check general-capability regressions after fine-tuning (13.6). Small models run on CPU slowly.

Phoenix · Langfuse
datasets · experiments · traces

Store eval datasets, run experiments, attach scores to production traces (chapter 17). Both self-hostable.

The numbers

Reliability over repeated runs. If an agent succeeds 95% of the time per run, all 5 of 5 runs succeed only 0.95 multiplied by itself 5 times ≈ 77% of the time. At 99% per run it is about 95%. Daily workflows need per-run success very close to 100%.

The cost of steps. An agent that takes 12 steps of about 3,000 tokens each uses 36,000 tokens per task. If a better prompt cuts that to 6 steps, it halves the cost and the time, even with the same success rate, which is why step counts belong in the evaluation.

Code

The program checks four recorded agent runs for allowed tools, step limits, checking the order before acting, the right end state and an honest final message, then works out pass@3 and pass^3. Edit a run in RUNS to fix or break it and run it again.
