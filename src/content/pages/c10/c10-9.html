Intuition

The advanced methods each fix one specific kind of failure. Searching summaries first helps with "big picture" questions. Matching token by token helps when exact details matter. A knowledge graph helps with questions about connections between things. An agent that searches several times helps with messy questions that need several sources.

Each one costs money, speed and complexity, so they are tools for a diagnosed problem, not upgrades to apply by default. Measure first, then add the one that fixes what you measured.

Mechanism

These techniques help specific failure patterns and add cost and complexity. Adopt one only when evaluation shows (a) the failure pattern is common in your queries and (b) the technique fixes it on your benchmark by more than simpler fixes (better parsing, hybrid search, reranking, query rewriting).

Example: evaluation-driven adoption

A team considering GraphRAG labels 300 real queries by type and finds only 6% are multi-hop. On those, GraphRAG improves accuracy from 41% to 63%, but query-decomposition (9.6) with the existing index reaches 58% at a fraction of the cost. They adopt decomposition and revisit graphs if multi-hop traffic grows.

Train and use ColBERT-style multi-vector models built on Sentence Transformers.

GraphRAG

Entity/relation extraction, community summaries, local and global search. Indexing is LLM-call heavy; try on a small corpus.

The numbers

Is it worth it? In the example below, 6% of 300 queries are multi-hop: 18 queries. Raising their accuracy from 41% to 63% fixes about 4 more answers, which moves overall accuracy by about 1.3 points, while every query pays for a more complex system.

What late interaction stores. A single 768-number int8 vector per chunk is 768 bytes. One 128-number vector per token, for 300 tokens at 2 bytes each, is 300 × 128 × 2 = 76,800 bytes: about 100 times more storage per chunk.
