Intuition

A PDF is a picture of a page, not a document with structure. Inside, the words may be stored as letters placed at positions, in any order, with columns, headers and page numbers mixed together. Tables are just numbers floating near each other, and scanned pages have no text at all, only an image.

So before anything can be searched, the page has to be read back the way a person reads it: in the right order, with headings recognised, tables rebuilt as rows and columns, and scans turned into text. When a RAG system "cannot find" something that is clearly in a document, bad parsing is usually why.

Mechanism

Real corpora are messy. A PDF is a page-description format: text may be stored as positioned glyphs with no reading order, columns, headers and footers mixed into the text stream, tables as lines and loose numbers, and scanned pages as images with no text at all.

  • Born-digital PDFs: extract text with layout analysis (reading order, columns, headings) using tools like PyMuPDF, pdfplumber or Docling.
  • Scanned documents: need OCR (optical character recognition: image → text). Classic engines (Tesseract) are CPU-friendly; deep-learning OCR and vision-language models are more accurate on poor scans and handwriting but GPU-hungry. Record OCR confidence; low-confidence pages need review or a better model.
  • Tables: flattening a table to a text line loses which number belongs to which column. Extract tables as structured data (rows × columns), then store them as Markdown/HTML in a chunk, or as one row-as-sentence per chunk ("Plan: Pro; Monthly price: €49; Seats: 10"), and keep the original for display.
  • Images and diagrams: generate captions/descriptions with a vision-language model, OCR any text in the image, and index those; link back to the image. Multimodal embeddings can index images directly.
  • Structure: preserve the heading hierarchy, list numbering, page numbers and section IDs as metadata. They improve chunking (9.2), filtering and citations ("Policy 4.2, page 17").
Example: a table that breaks naive extraction

A pricing PDF table flattened by naive text extraction reads "Basic Pro Enterprise 19 49 Contact 5 10 Unlimited". The question "how many seats does Pro include?" retrieves it, but the model guesses. Table-aware extraction stores "| Plan | Price | Seats |" rows, and the answer "10 seats" becomes reliable.

The numbers

OCR at scale (illustrative). If a classic OCR engine takes about 1.5 seconds per page on one CPU core, a million scanned pages take 1,500,000 seconds, about 17 days on one core, or about 6.5 hours on 64 cores. GPU-based OCR is faster and more accurate on poor scans, and costs more per hour.

Why tables need rows. The flattened table in the example reads "Basic Pro Enterprise 19 49 Contact 5 10 Unlimited". Nothing in that text links "10" to "Pro" and "seats". Stored as "Plan: Pro; Monthly price: 49; Seats: 10", the answer is in one self-contained sentence.

# pip install pymupdf docling
import fitz                                   # PyMuPDF: fast, born-digital text
doc = fitz.open("sample.pdf"); print(doc[0].get_text("text")[:800])
from docling.document_converter import DocumentConverter   # layout + tables (+ OCR); slower, CPU OK
res = DocumentConverter().convert("sample.pdf"); print(res.document.export_to_markdown()[:1500])

Use a PDF with a table and two columns. Docling downloads layout models on first run and is much slower than PyMuPDF on CPU; that difference is exactly why production pipelines route documents to different parser pools.
