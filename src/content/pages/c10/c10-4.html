Intuition

A knowledge base is never finished. Documents are edited, deleted, copied and moved every day, and the search index has to follow. Rebuilding everything every night is like reprinting a whole encyclopaedia because one page changed; instead, find exactly what changed and update only that.

Deletions matter most. A document someone deleted, or stopped sharing, must vanish from search quickly, and you need a paper trail for every chunk so you can always answer "where did this come from, and is it still current?".

Mechanism

  • Incremental updates: process only what changed. Use source change feeds (webhooks, delta APIs, database CDC) or periodic diffing by content hash. Re-chunk changed documents and replace their chunks atomically (delete old chunk IDs for that document version, insert new).
  • Deletions: a deleted or unshared source document must disappear from the index, caches and any derived summaries. Many connectors miss deletes unless you reconcile periodically (list all IDs at the source, diff with the index). Deletion speed can be a legal requirement (16.5).
  • Deduplication: the same file is often copied across sites and versions. Exact duplicates via content hash; near-duplicates via MinHash (6.2). Keep one canonical chunk set but remember all locations, because each copy may have different permissions.
  • Lineage: for every chunk, record source system, document ID, version, parser version, chunker config, embedding model version and timestamps. Lineage answers "why did the assistant say this?" and "which chunks must be rebuilt after the parser bug fix?".
  • Freshness guarantee: a measurable target such as "99% of edits searchable within 10 minutes; deletions within 5 minutes". Measure it by tracking indexed_at − source_modified_at per change (17.7).
  • Out-of-order events: change events can arrive late, twice or out of sequence. Apply them through the version guard from 10.2 and let periodic reconciliation repair anything a missed event left stale.
Example: the missed deletion

A contract is deleted from SharePoint, but the connector only processes "modified" events. Three weeks later the assistant still quotes it. The nightly reconciliation job (list all source IDs, diff with the index) is added; it finds 1,840 orphaned documents on its first run. A deletion-lag metric with a 5-minute SLO now alerts if this regresses.

The numbers

The diff against the rebuild. If 1% of 65 million chunks change in a day, an incremental update re-embeds 650,000 chunks. A nightly rebuild would re-embed all 65 million, a hundred times the work, and still leave changes waiting up to a day.

Measuring freshness. For each change, record when it happened at the source and when it became searchable. "99% within 10 minutes" means that out of 10,000 edits, at most 100 took longer, and you can show the list.

A missed deletion. If deletions arrive only as events and 0.1% of events are lost, then out of 50,000 deletions a year about 50 documents stay searchable forever, unless a regular reconciliation compares the full list of source ids with the index.

Code

The program gives every chunk of your example project’s documents an id built from its document, position and content, then edits one document, deletes one and adds one, and works out exactly which chunks to embed and which to delete. Edit a second document in the code and run it again.
