Intuition

Each embedding model has its own private language of numbers. Vectors made by one model mean nothing to another, like trying to find a book with a catalogue written in a code you do not have. So switching models means re-embedding everything and building a new index next to the old one.

Do it like moving house carefully: set up the new place completely, check it works, move in, and keep the old keys for a while in case you need to go back.

Mechanism

Vectors from different embedding models live in different spaces; you cannot compare a query embedded with model B against documents embedded with model A. Changing the embedding model (or its dimensions, or even the chunker) therefore requires re-embedding the whole corpus, which at scale takes days and real money. Treat it like a database migration with a blue/green pattern:

Example: the version bound together

An index is not just vectors: it is (embedding model + version, dimensions, normalisation, chunker config, parser version, ANN parameters). Store these as an index manifest. A query service that loads the manifest and refuses to query an index whose embedding model differs from its own prevents the silent failure where cosine scores look fine but results are random.

The numbers

What a migration costs, for the 65-million-chunk corpus in 10.1:

  • Storage: both indexes live side by side during the change, so 218 GB becomes about 436 GB until the old one is retired.
  • Re-embedding: about 33 billion tokens, roughly $660 through an illustrative hosted API, or 65,000,000 ÷ 2,000 chunks a second ≈ 9 hours on one GPU.
  • Comparison: run real queries through both and check how much their top results agree before switching. If they share only half of their top 5, look at the differences before trusting the new one.
