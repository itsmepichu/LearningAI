The assistant must never reveal content the asking user cannot open in the source system. Since the LLM sees whatever is retrieved, enforcement must happen in retrieval, before content reaches the prompt.

  • Early binding (index-time): store each chunk's allowed principals (user IDs, group IDs) as metadata; at query time, filter by the user's group memberships inside the search. Fast; correctness depends on keeping ACLs in sync.
  • Late binding (query-time check): after retrieval, check each candidate against the source system's permission API. Always current; slower and can return too few results, so over-fetch.
  • Common practice: early binding for filtering plus a late check for high-sensitivity sources, with short ACL sync intervals and immediate updates on permission-change events.
  • Tenant isolation: tenant ID is a mandatory, server-set filter on every query (never taken from the prompt or model output), ideally reinforced structurally (separate collections, namespaces or encryption keys for sensitive tenants). Test it with cross-tenant probing cases (16.4).
  • ACL sync: group memberships change constantly. Sync group expansions from the identity provider; handle nested groups; treat "unknown ACL" as deny.
  • Urgent revocation: index-level ACL sync always has some lag. Keep a small deny list (revoked users, groups or documents) checked against the authoritative source on every query until the sync catches up. Cache keys must include the user's access scope and the policy version, so a revocation also invalidates cached answers.
Example: the stale-ACL incident

An employee moves from Finance to Sales at 09:00. The identity provider updates instantly, but the RAG index syncs group expansions nightly. At 14:00 they ask about "Q4 forecast" and receive Finance-only content. Fix: subscribe to group-change events, set an ACL-lag SLO, and add late-binding checks for sources tagged confidential.
