Model APIs are stateless: each call must include everything the model should know. "Conversation memory" is something your application builds by resending history. As conversations grow, they approach the context limit and every turn gets slower and costlier, so you need a strategy:

  • Sliding window: keep the last N turns. Simple; forgets early facts ("my account ID is…").
  • Summarise and window: keep a running summary of older turns plus recent turns verbatim.
  • Extract facts: pull durable facts (preferences, IDs, decisions) into a structured store and inject them as needed.
  • Persistent memory: facts that outlive a session (user prefers metric units; works on project X) stored in a database or vector store, retrieved by relevance, with user visibility and deletion controls (11.4, 16.5).

Store the full transcript in your own database regardless; the model's context is a working view, not the system of record. Some providers offer server-side conversation state, which is convenient but still needs your own records for audit and evaluation.

Example

In turn 3 a user says "I'm on the EU data-residency plan". In turn 40 they ask "can I use the new US-only feature?". A pure sliding window has lost turn 3 and answers "yes". Fact extraction keeps plan: EU-residency in every context, and a deterministic rule (7.7) blocks the US-only feature.
