Intuition

Free text is for people; programs need data. Asking a model for structured output is like giving it a form to fill in instead of a blank page: the answer comes back in fields your code can read. Tool calling goes one step further: the model fills in a request form ("please look up order A-1043"), and your code decides whether to run it.

The model never acts by itself. It only asks. Your code checks every request, runs the ones that are allowed, and hands back the result.

Mechanism

Structured output: the model returns data in a declared format, usually JSON matching a JSON Schema. Many APIs and local engines support constrained decoding, which masks tokens that would break the schema, so the output always parses.
Schema validation: parse and check the output in code (e.g. Pydantic). Constrained decoding guarantees shape, not truth: a valid JSON with a wrong amount is still wrong, so add semantic checks.
Tool calling (function calling): you describe functions (name, description, parameter schema); the model may answer with a request to call one with arguments; your code executes it and returns the result as a tool message; the model continues.
Streaming: receive tokens as they are generated (usually Server-Sent Events) instead of waiting for the full response. Improves perceived latency; complicates validation and error handling.

The numbers

Failures at volume. If 2% of free-form answers fail to parse, 100,000 calls a day means 2,000 retries a day. Constrained decoding brings shape failures close to zero, but an answer can still parse and be wrong, so semantic checks stay.

Why streaming feels faster. A 200-token answer at 50 tokens per second, after 0.4 seconds to the first token, takes 0.4 + 200 ÷ 50 = 4.4 seconds to finish either way. With streaming, the reader starts reading at 0.4 seconds instead of staring at a spinner for 4.4.

Laptop lab: structured output, tool call and streaming with Ollama Laptop · CPU
# pip install ollama pydantic ; ollama pull qwen2.5:1.5b
from typing import Literal
from pydantic import BaseModel, ValidationError
import ollama

class Ticket(BaseModel):
    category: Literal["billing", "access", "delivery", "other"]
    urgent: bool
    summary: str

msg = [{"role": "user", "content": "Since 9am nobody in my team can sign in. We have a launch today!"}]
r = ollama.chat(model="qwen2.5:1.5b", messages=msg, format=Ticket.model_json_schema(), options={"temperature": 0})
try:    print(Ticket.model_validate_json(r.message.content))
except ValidationError as e: print("invalid output:", e)       # always handle this path

def get_order_status(order_id: str) -> str:
    """Look up the shipping status of an order by its ID."""
    return {"A-1043": "shipped 2026-11-02"}.get(order_id, "not found")

r = ollama.chat(model="qwen2.5:1.5b", tools=[get_order_status],
                messages=[{"role": "user", "content": "Where is order A-1043?"}])
for call in r.message.tool_calls or []:
    print(call.function.name, call.function.arguments, "->", get_order_status(**call.function.arguments))

for chunk in ollama.chat(model="qwen2.5:1.5b", messages=msg, stream=True):
    print(chunk.message.content, end="", flush=True)

Small models make more tool-call mistakes (wrong arguments, calling when not needed). That is useful: you will see the failure modes your validation must handle.
