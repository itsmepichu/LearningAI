A prompt is the program you give the model. Messages usually have roles: system (persistent instructions from the developer), user (the request), assistant (prior model replies), and tool (results of tool calls). A well-structured prompt has distinct parts:

  1. Role and goal: who the model is acting as and what success looks like.
  2. Instructions and constraints: specific, positive ("answer in under 80 words"), with the reason when it helps the model generalise.
  3. Context: documents, data, user profile; clearly delimited (e.g. XML-style tags) so the model knows what is data versus instruction.
  4. Examples (few-shot): 2–5 input→output pairs showing format and edge cases. They are very strong signals; make them diverse so the model does not copy surface details.
  5. Output format: a schema or template.
  6. The input itself, last.

Prompt versioning. Treat prompts as code: store them in the repository or a prompt registry with an ID and version (ticket_triage@v7), review changes, run the evaluation set on every change, and log the prompt version with every production request so any output can be traced to the exact prompt that produced it (18.1).

Example: a versioned prompt file
# prompts/ticket_triage/v7.yaml
id: ticket_triage
version: 7
model: provider/model-name-2026-xx      # pinned snapshot, not an alias
params: {temperature: 0, max_tokens: 200}
system: |
  You classify customer support tickets for Acme Cloud.
  Categories: billing, access, delivery, other. Use "other" when unsure.
  Mark urgent only for outages, data loss or security concerns, not for angry tone.
  Respond with JSON matching the schema. Do not add commentary.
examples:
  - in: "I was charged twice this month"           out: {"category":"billing","urgent":false}
  - in: "Nobody on my team can log in since 9am"   out: {"category":"access","urgent":true}
changelog: "v7: clarified urgency rule after eval case #118 regression"
