Intuition

Model APIs are like a busy restaurant phone line: sometimes engaged, sometimes slow, occasionally down. A good caller does not hold forever (timeouts), does not redial instantly and endlessly (backoff), and does not have everyone in the office redial at the same second (jitter). If the line stays dead, they try the other restaurant (fallback).

And because every call costs money, set budgets: how long an answer may be, how much context may be sent, and how much each customer may spend in a day.

Mechanism

  • Timeouts: set a connect timeout and a total deadline per call; for streaming, also an idle timeout between tokens. LLM latency has a long tail; without timeouts, threads and connections pile up.
  • Retries: retry only retryable errors (timeouts, HTTP 429 rate-limited, 5xx, connection resets), with exponential backoff and jitter (wait base × 2attempt, randomised) to avoid synchronised retry storms. Respect Retry-After headers. Cap attempts and total time. Never blindly retry a call that triggered side effects (11.6).
  • Rate limits: providers limit requests per minute and tokens per minute. Track both client-side (a token bucket) so you queue rather than get rejected.
  • Fallbacks: on repeated failure, switch to a secondary model or provider, a cached answer, or a graceful message. Fallback models must be evaluated too, since output quality and format may differ.
  • Token budgets: cap input tokens (truncate context), output tokens (max_tokens), and per-user / per-tenant daily spend.
Example: a call wrapper
import random, time
RETRYABLE = {408, 429, 500, 502, 503, 504}
def call_llm(req, primary, fallback, deadline_s=30, max_attempts=4):
    start = time.monotonic()
    for attempt in range(max_attempts):
        remaining = deadline_s - (time.monotonic() - start)
        if remaining <= 0: break
        try:
            return primary.generate(req, timeout=min(remaining, 20))
        except ProviderError as e:
            if e.status not in RETRYABLE: raise                     # 400 = our bug; don't retry
            wait = e.retry_after or random.uniform(0, 0.5 * 2 ** attempt)   # full jitter
            time.sleep(min(wait, max(0, deadline_s - (time.monotonic() - start))))
    return fallback.generate(req, timeout=10)                       # evaluated fallback path

The numbers

Backoff adds up. Waits of 1, 2, 4 and 8 seconds total 15 seconds over four retries, so the overall deadline must allow for them, or the last retries are pointless.

Why jitter. If 30 clients fail together and all wait exactly 1 second, all 30 retry in the same instant. With full jitter, each waits a random time between 0 and 1 second, and the busiest quarter-second gets roughly a third as many retries.

A rate limit in practice. A limit of 60,000 tokens per minute is 1,000 per second. Twenty requests of about 900 tokens arriving together need 18,000 tokens: a token bucket queues them over about 14 seconds instead of rejecting most of them.
