A model's output is a suggestion drawn from a distribution. Business rules (pricing, eligibility, permissions, compliance limits, workflow state) must be exact, auditable and identical every time. The core design pattern is: the model interprets and proposes; deterministic code validates, decides and executes.

  • Let the model do what is fuzzy: understand intent, extract fields from free text, draft wording, rank options.
  • Let code do what is exact: compute amounts, check limits, enforce permissions, choose state transitions, format legal text.
  • Keep the boundary explicit: the model outputs a typed proposal; a rules engine or plain code accepts, modifies or rejects it, and logs why.
Example: what goes wrong otherwise

A team prompts "Apply a 10% discount for customers over 2 years, max $500". In testing it works. In production, the model sometimes gives 15% to persuasive customers, rounds differently, and once applies it to a 1-year customer who claimed otherwise. Moving the rule into code with the model only extracting "customer requests loyalty discount" makes the behaviour exact, testable and auditable.

Toolbox for LLM applications

Ollama
local models · CPU OK

One-command local model runtime with a REST API, OpenAI-compatible endpoint, tool calling, structured outputs and streaming. The default for this course's labs.

llama.cpp
CPU/GPU inference · GGUF

Efficient C/C++ inference; llama-server exposes an OpenAI-compatible API with JSON-schema/grammar constrained output. Use for benchmarking (14).

LiteLLM
unified API · gateway

One interface for 100+ providers, plus a proxy with retries, fallbacks, budgets and rate limits. Point it at Ollama locally to prototype a model gateway (15.5).

Pydantic · Instructor
schemas · validation

Define output types in Python and validate model output; Instructor adds automatic re-asking on validation failure.

Outlines
constrained generation

Guarantees output matches a regex, JSON Schema or grammar for local models via token masking.

DSPy
programmatic prompting

Write LLM pipelines as modules and let optimisers tune prompts and examples against your metric. Use after you have an eval set.
