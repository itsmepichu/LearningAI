You do not have to choose before you start: everyone begins with Harbor. Switch at any time from the Example picker in the top bar, or use the project tabs on a topic's In practice block to read another project's version for that topic only. Each version has three parts: In practice (the idea applied to that system), Failure to avoid (the most likely mistake there) and Try it (exactly what to change in the topic's interactive figure, or what to run on your laptop, with that project's data). When another project suits a topic better, a short note at the end of the topic says so and lets you try it.

Each project has a small synthetic dataset you can download from any In practice block: support tickets and policies for Harbor, products, reviews and orders for the store, transactions and disputes for the bank, bookings and fare rules for travel. They contain realistic traps on purpose: a rare class, a column that leaks the answer, and a period where the data shifts.

Each chapter ends with

  • A lab with numbered steps, a Keep as evidence deliverable and a pass condition, sized to run on a laptop wherever possible, plus a scenario for your example project where one has been written.
  • A chapter check on its own page, grouped by section: choose-the-answer questions with explanations of every option, and likely interview questions with a checklist of what a strong answer covers. Use Practice mode for feedback after each answer or Check mode to score a whole section.
  • A Mark chapter studied button. Tick topics as you go; your progress shows in the sidebar and is stored only in this browser.

The Practice page (in the sidebar) draws on every chapter check: filter by chapter, learning path, question type, level or project, draw a random set, review the questions you got wrong, or run an interview drill one question at a time.

Press / or the Search button to search every explanation, example, lab and practice note, including the other projects' notes.

Lab rules
  • Use synthetic or public data and synthetic test tenants. Never put real customer or employee data into a learning exercise.
  • Keep API keys on the server side or in environment variables, never in prompts, notebooks you share, or the repository.
  • Label anything that calls a paid or external service, and set a spending limit before you start.
  • No model available? Run stubbed outputs through the same validators and checks, and label the results as mocked.
  • Say what each result does and does not prove ("300-example toy sample; does not establish production accuracy").

Your laptop setup (do this once)

Laptop lab Laptop · CPU

Create one isolated Python environment for the whole course. uv is a fast package manager; plain python -m venv works too.

# 1. Python environment
uv venv ai-course && source ai-course/bin/activate     # Windows: ai-course\Scripts\activate
uv pip install numpy pandas matplotlib jupyterlab scikit-learn
uv pip install torch --index-url https://download.pytorch.org/whl/cpu   # CPU-only PyTorch build
uv pip install transformers datasets sentence-transformers faiss-cpu bm25s pydantic

# 2. Local model runtime (pick one)
#    Ollama: install from https://ollama.com, then:
ollama pull llama3.2:1b          # ~1.3 GB, usable on CPU
ollama pull qwen2.5:1.5b         # alternative small model
#    llama.cpp: https://github.com/ggml-org/llama.cpp (prebuilt binaries in Releases)

# 3. Optional: Docker for vector databases, tracing and dashboards
docker --version

Limitations to expect: small models (0.5–3B parameters) run at a few to a few dozen tokens per second on CPU. They are good enough to learn APIs, prompting, RAG plumbing, agents and evaluation, but they reason worse than large hosted models. When a lab needs quality, call a hosted API instead and keep the rest of the code the same.
