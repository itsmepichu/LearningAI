• Shadow deployment: send a copy of production requests to the new version, discard its outputs (users see the old version), and compare: output differences, judge scores, latency, cost, errors. No user risk; for agents, shadow only with side-effect-free (mocked) tools.
  • Canary: route a small share of real traffic (1–5%) to the new version, compare its metrics with the baseline on the same time window, and promote automatically if healthy.
  • Controlled rollout: increase exposure in steps (5% → 25% → 50% → 100%), optionally by tenant cohort (internal users first, then low-risk tenants), with feature flags controlling which prompt/model/index version each cohort gets.
  • Rollback: one action, minutes not hours: flip the flag or alias back. Requires the previous version to still be deployed and compatible (for indexes, keep the old one warm: 10.7). Practice it.
  • Rollback does not undo actions: messages sent, refunds issued and tickets created by the bad version stay done. Plan reconciliation or compensation for them. Shadow traffic must never reach write tools: stub or disable side effects in shadow mode.
