Intuition

New versions meet real users gradually. A shadow deployment lets the new version answer real requests in private, so you can compare without anyone seeing its answers. A canary then gives it a small share of real users and compares the two side by side.

Each step widens only if the numbers stay within bounds, and any breach sends traffic back automatically. Rollback has one limit: it cannot unsend an email or reverse a refund, so shadow traffic must never reach tools that change things.

Mechanism

  • Shadow deployment: send a copy of production requests to the new version, discard its outputs (users see the old version), and compare: output differences, judge scores, latency, cost, errors. No user risk; for agents, shadow only with side-effect-free (mocked) tools.
  • Canary: route a small share of real traffic (1–5%) to the new version, compare its metrics with the baseline on the same time window, and promote automatically if healthy.
  • Controlled rollout: increase exposure in steps (5% → 25% → 50% → 100%), optionally by tenant cohort (internal users first, then low-risk tenants), with feature flags controlling which prompt/model/index version each cohort gets.
  • Rollback: one action, minutes not hours: flip the flag or alias back. Requires the previous version to still be deployed and compatible (for indexes, keep the old one warm: 10.7). Practice it.
  • Rollback does not undo actions: messages sent, refunds issued and tickets created by the bad version stay done. Plan reconciliation or compensation for them. Shadow traffic must never reach write tools: stub or disable side effects in shadow mode.
Example: rollout policy
rollout: kb-assistant r2026.11.3
steps:   [{weight: 0, shadow: 24h}, {weight: 5, hold: 2h}, {weight: 25, hold: 4h}, {weight: 50, hold: 12h}, {weight: 100}]
analysis (candidate vs baseline, same window):
  error_rate:          max_delta: +0.3pp
  p95_ttft_ms:         max_ratio: 1.15
  groundedness_sample: min_delta: -1.5pp   (500 sampled traces, judge@v4)
  thumbs_down_rate:    max_delta: +1.0pp
on_failure: set weight 0, page owner, attach comparison report

The numbers

How much a canary sees (illustrative). At 100,000 requests a day, a 5% canary for 2 hours sees about 100,000 × 0.05 × 2 ÷ 24 ≈ 420 requests.

  • With 500 judged samples, a groundedness of 95% is measured to within about ±2 points, so a drop to 90% is visible, but a drop to 94% is not.
  • If a bad version is caught at 5%, only 1 in 20 users met it; caught at 50%, half of them did.

Code

The program steps a candidate through 5%, 25%, 50% and 100% of traffic, compares sampled errors and groundedness with the baseline at each step, and rolls back on a breach. Make the regression smaller, from 0.95 to 0.93, and see whether 500 samples still catch it.
