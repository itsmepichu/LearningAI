Intuition

An AI system’s behaviour depends on much more than its code: the prompts, the models, the search index, the settings and even the evaluation suite that approved it. Change any one and the answers can change.

A release manifest lists all of them under one id, and every request records that id. When someone complains about an answer, you know exactly which combination produced it and can reproduce it.

Mechanism

Every artefact that can change behaviour needs an immutable version, and every production request should record the versions that served it. Bundle them into a release manifest: one identifier for "the system as deployed".

Example: manifest file
release: r2026.11.3
code: {commit: 7f3c2e1, image: registry.local/kb-api@sha256:9b1e…}
prompts: {answer: v12, triage: v7, rewrite_query: v3}
models: {answer: provider-a/large-2026-09, triage: pool/small-8b@ft-r431, judge: provider-b/mid-2026-06}
index: {alias: kb-search, target: kb-v4, embedder: bge-base@rev2, chunker: v5}
config: {retrieval_k: 8, rerank_top: 50, temperature: 0.2, flags_revision: 41}
evaluation: {suite: v31, judge_prompt: v4, results: s3://evals/r2026.11.3/}
approved_by: [kb-owner, sec-review]   created: 2026-11-03T16:20Z

The numbers

How many combinations (illustrative). With 3 prompts, 3 models, 2 index versions and 4 configuration sets in use over a quarter, there are 3 × 3 × 2 × 4 = 72 possible combinations. Without a manifest, "which version answered this?" has 72 possible answers.

Bisecting. If quality dropped somewhere across 16 releases, comparing the middle release first and halving each time finds the culprit in about 4 steps, since 2 × 2 × 2 × 2 = 16.

Code

The program hashes a manifest of code, prompts, models, index, configuration and evaluation suite into a release id, shows that changing only a prompt makes a new release, and finds which release served a complaint. Change the index target and run it again.
