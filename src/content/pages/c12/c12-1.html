Intuition

One person can read a report. Reading a library takes a team: each person reads a shelf and writes a one-page summary, and someone combines the pages. That is the honest case for a multi-agent system: more material, or more kinds of tools and permissions, than one agent can handle well.

A team also costs more: briefs, summaries, meetings. If you can write down the split yourself, "summarise each of these 20 contracts, then compare", do it in code with parallel calls. Let agents plan only when the plan really cannot be written in advance.

Mechanism

Multiple agents help when at least one of these is true:

  • Breadth exceeds one context: the task needs reading far more material than fits in one window (research over 200 documents), so parallel workers each read a part and return condensed findings.
  • Separable expertise or tools: different subtasks need different tools, permissions or instructions (a billing agent with payment tools, an account agent with identity tools), and mixing them in one prompt degrades tool selection.
  • Independent verification: a separate reviewer with a fresh context catches errors the producer is blind to.
  • Organisational boundaries: agents owned by different teams or vendors must interoperate.

They do not help when subtasks are tightly coupled (each needs the others' full detail), when the task is short, or when a plain parallel workflow works: if you can write the decomposition in code ("summarise each of these 20 contracts, then compare"), do that with parallel LLM calls. That is cheaper and more predictable than letting a coordinator agent discover the same plan.

Example

"Summarise customer complaints about onboarding in Q3 across support tickets, sales notes and app reviews." Three sources, different tools and access rules, ~40,000 records. A coordinator assigns one worker per source; each worker searches, clusters and returns a 300-word summary with evidence IDs; the coordinator synthesises. A single agent would exhaust its context in the first source.

The numbers

Does it fit in one context? (illustrative). A 128,000-token context can use about 96,000 tokens for material once instructions and the answer have room.

  • 40,000 records × 60 tokens = 2.4 million tokens. One agent sees 96,000 ÷ 2,400,000 = 4% of it.
  • Split among workers that each read 96,000 tokens: 2,400,000 ÷ 96,000 = 25 workers.
  • Each returns a 400-token summary: 25 × 400 = 10,000 tokens for the final step, which fits easily.

The overhead. Briefs, plans and summaries add tokens on top of reading. When reading dominates, that is a few per cent; on a small task it can be more than the useful work.
