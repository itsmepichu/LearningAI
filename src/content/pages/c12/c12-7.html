Intuition

A building receptionist with a master key is dangerous if anyone can ask them to open any door. That is the confused deputy: a helper with broad rights doing things for someone who should not have them.

The fix is to carry the requester’s identity along the chain and let each hop only narrow it. Each agent swaps the token it received for a smaller one that works only at the next service (token exchange), and the service itself makes the final decision.

Mechanism

When agent A asks agent B to act, whose permissions apply? The safe default: the original user's, narrowed at each hop. Problems arise when an agent with broad service credentials acts for users with fewer rights (the confused deputy problem).

  • Propagate user identity: pass a token representing the user (or an "on-behalf-of" token) through the chain, not just a user ID string that any agent could forge.
  • Token exchange (OAuth 2.0 Token Exchange, RFC 8693): each hop exchanges the incoming token for a new one with a narrower audience (only valid at the next service) and narrower scopes. Tokens are short-lived.
  • Agent identity too: each agent has its own workload identity (e.g. SPIFFE/mTLS or a service principal), so logs show "agent B acting for Alice, requested by agent A".
  • Authorise at the resource: the tool/API makes the final access decision using both identities; agents never decide access for themselves.
Example: the confused deputy

A reporting agent runs with a service account that can read every department's data. An intern asks it to "include salary benchmarks from HR". The agent, holding the credential, complies. With on-behalf-of tokens, the HR API sees the intern's identity and denies the request; the agent reports that the data is not accessible.

The numbers

Permissions only shrink. Alice has 3 scopes: read invoices, write invoices, read reports.

  • Her sign-in token for the assistant carries those 3.
  • The coordinator exchanges it for a token to the finance service with 1 scope, read invoices.
  • The finance API allows a request only if both Alice and the token have the scope: read works, write is refused, even if the model asks.

Short lives limit damage. A token valid for 5 minutes that leaks can be misused for at most 5 minutes; a service password that never expires, indefinitely.

Code

The program signs Alice in, exchanges her token for a narrower one for the finance service, and shows a read allowed, a write refused, a wrong audience refused, and an intern’s request for salaries refused at the exchange. Give the intern another scope and run it again.
