Self-hosting cost is mostly fixed: you pay for GPU-hours whether or not they are busy. API cost is variable: you pay per token. Self-hosting wins only when (a) your volume is high and steady enough to keep GPUs well utilised, (b) a smaller open model meets your quality bar, or (c) data-control requirements force it. Include the full cost: GPUs (with redundancy and headroom), engineers and on-call, networking, storage, observability, idle capacity at night, and the opportunity cost of not using newer hosted models.

Example: reading the default numbers

20B tokens/month at $0.60/M via API = $12,000/month. Self-hosted at 2,500 tokens/s per GPU and 45% average utilisation, one GPU delivers ≈ 2.96B tokens/month, so 7 GPUs ≈ $12,800 plus $15,000 ops ≈ $27,800. The API is cheaper here; self-hosting wins only at several times the volume, higher utilisation, or with a much cheaper model.

Toolbox for inference serving

vLLM
GPU serving engine

OpenAI-compatible server with paged attention, continuous batching and prefix caching; includes benchmarking tools. A CPU backend exists (build-from-source/nightly wheels) for experimentation, far slower than GPU. The 14.7 Colab guide serves and benchmarks it on a free GPU.

SGLang
GPU serving engine

High-performance serving with radix-tree prefix caching and structured generation.

llama.cpp
CPU-friendly inference

llama-bench, llama-server, quantisation tools. Your laptop testbed for prefill/decode and quantisation.

LLM Compressor
quantisation for vLLM

Apply FP8, INT8, GPTQ/AWQ-style quantisation and sparsity, producing checkpoints vLLM serves. GPU

GuideLLM
capacity benchmarking

Sweeps request rates against an OpenAI-compatible endpoint and reports throughput and latency percentiles. Point it at llama-server on your laptop to learn it.

KServe · Ray Serve
deployment on Kubernetes / Ray

Model deployment, autoscaling and routing layers that wrap engines like vLLM.
