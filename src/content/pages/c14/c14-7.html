Intuition

A bus that waits to fill up carries more people per trip, but each passenger waits longer. Batching more requests together is the same: more tokens per second for the GPU, slower tokens for each user.

The right batch size is the largest one that still meets the latency target. Admission control keeps the server there: it caps how many conversations run at once, queues a few more, and turns the rest away quickly instead of letting everyone slow down.

Mechanism

Batching more sequences together raises throughput (total tokens/s per GPU) because the weight read is shared, but each step takes longer, so per-user latency rises. At some batch size the GPU becomes compute-bound and throughput plateaus while latency keeps growing. The operating point is chosen by the SLO: "maximise tokens/s subject to p95 ITL ≤ 50 ms and p95 TTFT ≤ 1 s".

Admission control protects that operating point: cap concurrent sequences per replica (e.g. vLLM max_num_seqs) and KV usage, queue extra requests with a bounded queue, reject or redirect when the queue's expected wait exceeds the deadline (15.6), and prioritise interactive traffic over batch.

GPU utilisation metrics need care: "GPU utilisation 100%" from nvidia-smi only means a kernel was running, not that compute units were busy. Prefer tokens/s, model FLOPs utilisation (MFU) for prefill, memory-bandwidth utilisation for decode, KV-cache usage and batch size.

The numbers

A decode step (illustrative: 16 GB of weights, 3,300 GB a second of memory bandwidth).

  • Batch of 1: reading the weights takes 16 ÷ 3,300 ≈ 0.005 seconds, so 200 tokens a second for one user.
  • Batch of 64: the weights are read once for all 64, but each sequence’s cache is read too. If the step takes 14.5 ms, the GPU makes 64 ÷ 0.0145 ≈ 4,400 tokens a second, and each user gets 1 ÷ 0.0145 ≈ 69.
  • Batch of 512: about 82 ms a step, over a 50 ms target, though the GPU’s total barely grows.

Code

The program computes the decode step time for growing batch sizes as the slower of reading memory and doing arithmetic, finds the largest batch under a 50 ms target, and simulates a bounded queue. Change ITL_SLO or BANDWIDTH and run it again.
