• Static batching: wait for N requests, run them together until all finish. Short requests wait for the longest one; new arrivals wait for the whole batch. GPU slots sit idle.
  • Continuous (in-flight) batching: the scheduler re-forms the batch at every decode step: finished sequences leave immediately and waiting requests join (their prefill is inserted, often split into chunks so it does not stall decoding: chunked prefill). Typically multiplies throughput several-fold.
  • Paged attention (vLLM, 2023): store the KV cache in fixed-size blocks (e.g. 16 tokens) allocated on demand, mapped through a per-sequence block table, like virtual memory pages. Eliminates the waste of pre-reserving max-length contiguous memory, so many more sequences fit. Blocks can be shared between sequences.
  • Prefix caching: if many requests share a prefix (system prompt, tool definitions, a long document), keep its KV blocks and reuse them, skipping that part of prefill. Big TTFT and cost win; hosted APIs expose this as "prompt caching" with discounted cached-input pricing. Structure prompts with stable content first (7.2).
Example: prefix caching economics

A support bot sends a 6,000-token system prompt + tool definitions with every request, plus ~800 tokens of conversation. With prefix caching, only ~800 tokens need prefill on a cache hit: TTFT drops from ~700 ms to ~120 ms (illustrative), and with a provider that discounts cached input, input cost drops by most of its value. Changing one character near the start of the system prompt (e.g. inserting the current time) breaks the cache for everything after it.
