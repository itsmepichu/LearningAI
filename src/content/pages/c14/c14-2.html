Prefill: process all prompt tokens in one parallel forward pass, filling the KV cache. Compute-bound: lots of matrix maths per weight read, so GPUs run near their FLOP limit.
Decode: generate one token per forward pass per sequence. Memory-bandwidth-bound: each step reads all weights (and the sequence's KV cache) to do a small amount of maths. Batching many sequences shares the weight read across them.
TTFT (time to first token): queueing + prefill time. Grows with prompt length. ITL / TPOT (inter-token latency / time per output token): time between streamed tokens. End-to-end latency ≈ TTFT + (output tokens − 1) × ITL.
Laptop lab: measure TTFT and ITL for real Laptop · CPU
# Start a local server first:  ollama serve   (or llama-server -m model.gguf --port 8080)
import time, ollama
prompt = "Summarise the following text in 3 bullet points:\n" + ("The cache stores keys and values. " * 300)
t0 = time.perf_counter(); first = None; n = 0
for chunk in ollama.generate(model="llama3.2:1b", prompt=prompt, stream=True, options={"num_predict": 120}):
    if chunk.response:
        n += 1; now = time.perf_counter()
        if first is None: first = now
    if chunk.done:
        print(f"TTFT {first - t0:.2f}s | {n} chunks | ITL {(now - first) / max(n - 1, 1) * 1000:.0f} ms"
              f" | engine: prefill {chunk.prompt_eval_count / (chunk.prompt_eval_duration / 1e9):.0f} tok/s,"
              f" decode {chunk.eval_count / (chunk.eval_duration / 1e9):.1f} tok/s")

Multiply the prompt length by 4 and re-run: TTFT grows roughly linearly while decode speed barely changes. That is prefill vs decode, measured on your own CPU. Run it twice: the second TTFT is lower because Ollama reuses the cached prompt prefix (14.3).
