Intuition

The most valuable test cases are the ones your system already failed in front of real users, because nobody thought to write them. The evaluation flywheel makes collecting them routine: flag bad traces, find the cause, turn each into a test case, fix the cause, and never ship a release that fails the growing suite.

Over months, the suite becomes an exact description of what your users need.

Mechanism

The most valuable evaluation data comes from production failures, because they are real and they were missed. Make the path from "bad trace" to "regression test" short and routine:

Example: from trace to test in one file
- id: prod-2026-11-02-0412
  source: {trace_id: "9a1c…", issue: "AI-882", reason: "cited outdated 2024 policy"}
  input: "What's the travel per-diem for Berlin?"
  context_snapshot: kb@2026-11-02          # pinned index snapshot for reproducibility
  expect:
    - type: contains_citation_from: {doc: "travel-policy-2026", section: "per-diem"}
    - type: not_contains: "2024"
    - type: judge_groundedness: {min: 1.0}
  tags: [freshness, policy, critical]

The numbers

A weekly review (illustrative). 2,000 flagged traces a week; reviewers sample 150 across tenants and features.

  • After removing duplicates, perhaps 100 distinct failures remain; if 60 are worth keeping, the suite grows by 60 cases a week, about 3,000 a year.
  • If 40% of them are retrieval failures, 24 a week point to retrieval rather than the prompt: fix the stage that fails most.

Code

The program turns flagged traces built from your project’s messages into evaluation cases: it redacts phone numbers, drops duplicates, keeps the trace link and tags the root cause. Add another redaction rule and run it again.
