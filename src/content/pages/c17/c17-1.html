Intuition

Logs are diary entries, metrics are the bathroom scale, and a trace is a parcel’s tracking history: every place one request went, in order, with how long each stop took.

What ties them together is an id that travels with the request, through services, queues and agents. With it you can go from "latency is up" to the exact slow request and every log line it produced. OpenTelemetry is the common way to produce all three and send them anywhere.

Mechanism

Logs: timestamped event records ("tool call failed: timeout"). Best as structured JSON with consistent fields.
Metrics: numeric time series aggregated over time (request rate, p95 latency, tokens/s). Cheap to store and alert on; no per-request detail.
Traces: the path of one request through the system as a tree of spans (timed operations with attributes), linked by a trace ID that propagates across services, queues and agents.
Correlation ID: an identifier attached to everything related to one request or task (logs, spans, DB rows, tickets), so you can find all of it. The trace ID usually serves this role; propagate it through queues and async jobs explicitly.
OpenTelemetry (OTel): the vendor-neutral standard and SDKs for producing traces, metrics and logs, plus the Collector that receives, processes (sample, redact, enrich) and exports them to any backend via OTLP.

Telemetry needs its own backpressure. Use batch exporters with bounded queues, timeouts and a drop policy, so a slow or unavailable telemetry backend never blocks request handling or exhausts memory. Count what gets dropped (17.6).

Example: a structured log line joined to its trace
{"ts":"2026-11-04T10:14:22.381Z","level":"warn","service":"rag-api","msg":"reranker timeout, using fused order",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"00f067aa0ba902b7","tenant":"acme",
 "feature":"kb-assistant","prompt_version":"answer@v12","timeout_ms":250}

The numbers

What each costs (illustrative), at 200 requests a second.

  • Metrics: a few hundred time series, a number every 15 seconds each: tiny, whatever the traffic.
  • Logs: 10 lines of 300 bytes per request = 200 × 10 × 300 × 86,400 ≈ 52 GB a day.
  • Traces with 25 spans of 1 KB each: 200 × 25 KB × 86,400 ≈ 430 GB a day, before sampling (17.6).

That is why metrics carry the alerts and traces are sampled.

Code

The program creates spans with trace and span ids, puts the trace context into a queue message as a W3C traceparent header, continues the trace in a "worker", rebuilds the span tree and finds the trace’s logs. Remove the header from the message and see the worker start a separate trace.
