Intuition

A good alert wakes someone only when users are being hurt and tells them where to start. Burn-rate alerts ask how fast the error budget is being spent: a sharp incident spends it in hours and pages at once; a slow leak spends it over days and opens a ticket.

Every alert links to a runbook: how to confirm, the first safe actions (a flag, a rollback, a degradation level), who to call, and how to know it is fixed. Afterwards, a blameless postmortem turns the incident into new tests and alerts.

Mechanism

  • Dashboards: one overview per service (SLOs, golden signals, AI signals, cost) with drill-downs per stage, model, tenant and feature. Put deploys, model changes and config changes as annotations.
  • Actionable alerts: alert on symptoms users feel (SLO burn), not on every cause. Use burn-rate alerts: page when the error budget is being consumed fast (e.g. 2% of a 30-day budget in 1 hour, a burn rate of 14.4), ticket when slow. Each alert links to a runbook.
  • Runbooks: for each alert, what it means, how to confirm, first mitigations (flags, rollbacks, degradation levels, failover), escalation contacts, and how to verify recovery.
  • Incident investigation: start from affected traces (exemplars linked from metrics), compare with healthy traces, check recent changes (deploys, prompt versions, model versions, index versions, provider status).
  • Postmortems: blameless write-up of timeline, impact, root causes, what went well, and action items with owners, including new evaluation cases and alerts.
Example: runbook excerpt
ALERT: kb-assistant groundedness below 92% (sampled judge, 2h window)
1. Confirm: open "AI quality" dashboard → groundedness by model_version, prompt_version, index_version.
2. Recent change? Check annotations: deploys, prompt registry, model alias changes, index cutovers.
3. If a provider model version changed in the window: switch gateway route to pinned previous
   snapshot (flag kb.model_pin=true). Verify recovery within 1h of sampled traffic.
4. If index_version changed: switch search alias back (10.7). Verify Recall@10 smoke test.
5. If neither: pull 30 low-scoring traces; classify retrieval vs generation failure (8.5); escalate to owners.
6. Record timeline in incident channel; create eval cases from failing traces (17.9).

The numbers

Burn rate with a 99.9% SLO, so a 0.1% error budget.

  • 1.44% errors in the last hour is 1.44 ÷ 0.1 = 14.4 times the sustainable rate. A 30-day budget lasts 30 ÷ 14.4 ≈ 2 days at that pace: page now.
  • One hour at 14.4 times uses 14.4 ÷ 720 hours = 2% of the month’s budget.
  • 0.2% errors for five days is only 2 times the rate, so the fast rule never fires; a 3-day window with a threshold of 1 catches it.

Code

The program generates 30 days of hourly error rates with a sharp incident and a slow leak, and finds when a fast page, a slow page and a ticket rule would each fire. Make the leak smaller and see which rule still catches it.
