Intuition

A dense model is a generalist who reads every request in full with everything they know. A mixture-of-experts model is a firm of specialists with a receptionist: each token is handed to the two or three specialists who suit it best, so the firm knows a lot but only a small part of it works on any one token. You still have to pay rent for the whole office, though: every expert must be in memory.

Context length has a cost of its own. With attention, every token looks at every other token, so a text twice as long means four times as many comparisons, and every token kept in context also takes memory.

Mechanism

In a dense model, every parameter is used for every token. In a mixture-of-experts (MoE) model, each FFN is replaced by many "expert" FFNs plus a small router that picks the top few experts (e.g. 2 of 8, or 8 of 128) per token. Total parameters grow, but active parameters per token stay small. Mixtral 8x7B, for example, has ~47B total parameters and ~13B active per token.

Tradeoff: MoE gives near-large-model quality at small-model compute per token, but all experts must sit in memory, so it needs as much memory as a dense model of its total size. Serving also needs good load balancing across experts (expert parallelism, 14.5).

Attention cost. Self-attention compares every token with every other, so compute and the score matrix grow with n² (sequence length squared). Doubling context quadruples attention compute. Optimised kernels such as FlashAttention avoid storing the full n × n matrix, but the compute is still quadratic. The KV cache grows linearly with n and is often the real memory limit in serving (14.1). Long contexts also have a quality cost: models use information in the middle of long contexts less reliably than at the start or end, so "fits in the window" does not mean "used well". Measure it on your task (9.5).

Example: stuffing the context vs retrieving

You could put a 400-page manual (≈ 250k tokens) in every prompt. Each request would pay for 250k input tokens, wait seconds for prefill, and need ~33 GB (≈ 31 GiB) of KV cache for an 8B model. Retrieving the 5 most relevant chunks (≈ 3k tokens) is roughly 80× cheaper in tokens and usually more accurate. Prompt caching (14.3) reduces the cost of repeated long prefixes, but not the quality issue.

The math

MoE layer. The router scores the E experts with r = xW_r, keeps the top k, and mixes their outputs with softmax weights over the kept scores:

y = \sum_{e \in \operatorname{TopK}(r,\,k)} g_e(x)\, \operatorname{FFN}_e(x), \qquad g_e(x) = \frac{e^{r_e}}{\sum_{e' \in \operatorname{TopK}(r,\,k)} e^{r_{e'}}}

With L layers, attention parameters A per layer and F per expert, the model stores and uses:

N_{\text{total}} = L\,(A + E\,F), \qquad N_{\text{active}} = L\,(A + k\,F)
\text{FLOPs per token} \approx 2\,N_{\text{active}}

Memory follows N_{\text{total}}; compute per token follows N_{\text{active}}. Training adds a load-balancing loss so the router does not send every token to the same few experts.

Attention and KV cache. For context length n and model width d, the score and weighted-sum products cost per layer, counting a multiply-add as 2:

\text{FLOPs}_{\text{attn}} \approx 4\,n^2 d, \qquad \text{KV bytes} = 2 \times L \times h_{kv} \times d_{\text{head}} \times b \times n

For an 8B-class model (L = 32, h_{kv} = 8, d_{\text{head}} = 128, b = 2 bytes in BF16) that is 131,072 bytes, or 128 KiB, per token: about 31 GiB for the 250k-token manual in the example above.
